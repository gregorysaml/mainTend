# Application architecture

Scenario 2 adds `shared/lubrication.ts`, a separate pure model/fixture/transactional repository in `backend/src/predictive/lubrication.ts`, and `LubricationWorkspace.tsx` for preview, graph, evidence, controls and notifications. `PredictiveWorkspace.tsx` coordinates cooling/lubrication tabs. The shared accessible popup is now `MaintenancePredictionsDialog.tsx`; system-aware fragment resolution validates profile, vehicle and snapshot without substituting another system's evidence. Lubrication uses separate immutable run, selection and read-state tables, leaving cooling snapshots and observations unchanged. Fleet lubrication is assigned to FLEET-003 only, cooling to FLEET-002; owner supports both on its single vehicle. See `LUBRICATION_SCENARIO.md`.

Vehicle header signals are derived by the pure `frontend/src/utils/vehicle-signals.ts` selector from the current assessment, selected matching demo snapshot and explicit forecast provenance. `VehicleIdentity` accepts typed indicators and renders responsive icon links in the unused identity-header space. Rule warnings stay distinct from synthetic cooling results, stale/historical outputs are not presented as current predictions, and neutral no-rule/data-gap labels do not claim a fault-free vehicle. Mileage source simplification is presentation-only through `mileageSourceLabel`; SQLite and evidence retain original provenance.

The cooling maintenance flow adds pure fragment navigation/scope/advice helpers in `frontend/src/features/predictive/presentation.ts` and a native accessible modal, now shared as `MaintenancePredictionsDialog.tsx`. `MaintenanceWorkspace` owns the URL-selected popup; preview links use fragment routes without a full-page reload. Predictions use the selected system's chart; recommendations compose the existing action form with busy/dirty callbacks; Service book reads existing profile/audit/action/inspection records. The popup itself requires no new backend endpoint or table. Demo controls and full evidence remain separate; cooling graph method and stored immutable snapshots are unchanged.

Cooling adds shared contracts/labels in `shared/cooling.ts`, pure calculation and deterministic fixtures plus transactional persistence in `backend/src/predictive/cooling.ts`, and a self-contained React feature in `frontend/src/features/predictive/`. Fixtures never enter observation tables. `cooling_runs` holds immutable snapshots (update/delete blocked), `cooling_selection` the chosen per-vehicle run, and `cooling_notifications` separate read acknowledgements. Warning `source_ref` links to the run; existing action/inspection links retain decision evidence. Profile checks are demo scope, not authentication. Overall evidence input hashes additionally cover cooling input hashes/selected snapshot identities, excluding read/task/inspection mutations. Held-out targets never enter the model fit or per-run input hash. See `COOLING_SCENARIO.md`.

Stage 5 adds `shared/inspection.ts` for verdict/provenance contracts and follow-up selection, `backend/src/maintenance/inspections.ts` for strict validation and transactional append-only storage, and `InspectionPanel.tsx` for the reusable result/form/history UI in both profiles. `action_inspections` references actions; warning linkage is inherited from the action, not copied into a mutable inspection field. The POST API checks vehicle-profile scope and latest inspection revision under an immediate transaction. Legacy completion notes/status history are unchanged, and no inspection writes to observations or warning state. JSON/CSV evidence includes reports; assessment input hashes remain measurement/configuration/forecast-only. See `INSPECTION_OUTCOMES.md`.

Stage 4 introduces shared discriminated edit contracts in `shared/vehicle-profile.ts`, backend validation/transactional writes in `backend/src/vehicles/`, and the five-section React editor plus browser-only image preparation in `frontend/src/features/vehicles/`. The SQLite adapter adds append-only profile audit history and revision conflict detection. Existing detail records are seeded only once, never merged over edited equipment/tyres on startup. See `VEHICLE_PROFILE_EDITOR.md`.

Stage 3 separates scheduling semantics into `shared/maintenance.ts`, input validation into `backend/src/maintenance/scheduling.ts`, and reusable React forms/task lists into `frontend/src/features/maintenance/`. An additive SQLite migration preserves existing action/history rows, adding due-date/priority fields and audit snapshots. Task/history creation and updates are transactional. `VehicleIdentity.tsx` and `utils/vehicle-identity.ts` provide reusable registration/model/mileage presentation. See `MAINTENANCE_SCHEDULING.md` for time semantics, API and verification.

Stage 2 adds a self-contained `frontend/src/features/fleet/` feature: pure tested selectors derive whole-fleet metrics, filtering, deterministic sorting and eligible-reading metadata; `FleetWorkspace.tsx` coordinates the summary, controls, filtered map and vehicle cards. Route parsing and profile-specific primary menu definitions live in `frontend/src/navigation/pages.ts`. The header utility route `#settings` is the only screen mounting `AssessmentControls`; mobile primary-navigation counts remain unchanged. No storage schema or API change was needed. See `FLEET_FILTERS.md`.

The codebase uses a layered modular monolith. It is intentionally one deployable local process, while responsibilities remain separated so the prototype can evolve without coupling the UI to SQLite.

```text
frontend (React + TypeScript)
    -> typed API client
backend HTTP/API composition (TypeScript)
    -> deterministic domain rules (TypeScript)
    -> persistence adapter (Node SQLite)
shared contracts (TypeScript) are used by frontend and backend
```

`frontend/src/api` owns network communication; view code does not construct backend URLs directly. `backend/src/core.ts` contains pure assessment logic. `backend/src/imports/normalization.ts` validates and converts observation inputs without HTTP or database dependencies. `backend/src/http/app.ts` exposes the API through an injectable server factory, allowing real HTTP tests against an isolated SQLite database. `backend/src/server.ts` composes and starts the local application. The persistence adapter owns relational storage, source metadata, transactions and foreign-key links. `shared/types.ts` defines vehicle, warning, action, assessment and import contracts.

This is a modular monolith rather than microservices. For the small research MVP, separate services would add operational complexity without producing stronger evidence. The boundaries are nevertheless suitable for later extraction if live ingestion or forecasting becomes an independent service.

`backend/src/assessment/settings.ts` validates the editable settings. `backend/src/evidence/report.ts` builds typed JSON snapshots and escaped, formula-protected CSV exports. `frontend/src/components/AssessmentControls.tsx`, `MeasurementHistory.tsx` and `VehicleProfile.tsx` separate configuration/export, SVG chart and vehicle-profile presentation. Pure series ordering and age classification live in `frontend/src/utils/measurements.ts` and are independently tested. No chart dependency or external image URL is needed.

SQLite keeps specifications, equipment, odometer history and tyre records in separate foreign-key-linked tables. The photo URL/description are stored in the database; the PNG is served as a local static asset copied into the production build. Additive schema initialization and idempotent synthetic seed extensions preserve existing observations and maintenance records.
