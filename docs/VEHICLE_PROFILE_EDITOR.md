# Stage 4 — editable profiles (B2B and B2C)

Fleet: Vehicles → Edit profile, in the vehicle-identity header directly below the mileage box. Owner: My vehicle → Edit profile, directly after mileage in the vehicle hero card. Each button retains a registration-specific accessible name. The button opens a modal popup containing all five sections and change history together, not an inline disclosure or one-section-at-a-time tabs. Each section saves independently and requires a change note. Saving a section resets only its own form; drafts in the other sections remain mounted and intact. Closing with unsaved changes asks whether to keep editing or discard the drafts; saved records are unaffected.

The native modal dialog uses accessible title/description, inert background, keyboard focus wrapping, Escape handling, focus return to the opener and background scroll locking. Header/close button and footer remain visible while the middle scrolls. Saving or photo preparation temporarily disables the controls/closing to avoid overlapping writes. Desktop uses a two-column layout, mobile a single-column popup. No backend/schema change was required for this UI revision.

- Mileage: append-only whole-kilometre readings (0–2,000,000), explicit UTC timestamp, no future time, duplicate instant or decrease across dated records. Source is `user entered`; existing readings stay intact.
- Service: latest recorded date/mileage, checked against mileage history. No service interval, reminder or diagnosis is inferred.
- Tyres: zero to four unique positions; edit/add/remove records including make/model/size/season/DOT, installation date/km, rotation date, pressure/tread and UTC measurement time. Calendar/order and numeric storage bounds are checked; bounds are NOT manufacturer recommendations or a safety assessment. Replacing/removing records retains before/after values in the audit trail.
- Equipment: up to 40 unique case-insensitive entries, up to 80 characters each. Empty list clears the current list, with the old list retained in history.
- Photo: local JPEG/PNG/WebP selection up to 5 MB, decoded and re-encoded by the browser, capped at 1280 px and under 500 KB. Metadata is stripped through canvas re-encoding. The backend checks strict data URL/base64, byte limit and raster signature, not a full image decoder. External image URLs and SVG uploads are rejected. Image data is stored in SQLite, not sent to an image service. Removal is explicit. Audit entries retain presence/description/SHA-256, not recoverable historical image bytes. The pre-existing AI demo image stays labelled illustrative; only user-uploaded photos replace the generic illustration in main identity cards.

`PATCH /api/vehicles/:id/profile` accepts exactly `{profile,revision,note,section,value}`. Shared discriminated contracts: `shared/vehicle-profile.ts`. Backend validation/transactional mutation: `backend/src/vehicles/`. React form/local image preparation: `frontend/src/features/vehicles/`. SQLite adds only `vehicle_profile_history`; prior tables/records remain. Revision is the latest audit-row ID for that vehicle (zero initially). Stale requests are rejected, not silently overwritten. Profile matching is scope validation, NOT authentication.

Field writes and audit entry commit together; failure rolls back. On API failure, the active draft remains. Stale-revision errors explain copying the draft before refreshing. Startup now skips already-initialized detail records so removed equipment/tyres/photos are not resurrected on restart.

Details remain part of a synthetic demonstration; user edits are unverified, not live telemetry. Per-section audit and odometer source distinguish edits from fixture data. History appears in JSON/CSV evidence. The evidence input hash still covers assessment inputs only, not profile edits/photo bytes. No observation, warning, action or assessment rule is changed by a profile edit.
